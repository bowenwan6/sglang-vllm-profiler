## 1. The change

A generation request may carry `waiting_timeout` (seconds). If it is still in the scheduler's waiting
queue after that long, the existing timeout scan drops it with the response `SGLANG_REQ_WAITING_TIMEOUT`
already produces. Both bounds apply, so a request can shorten the operator's bound, not extend it.
49 added and 3 removed source lines in 7 files, 7 unit cases, two documentation rows. PR-ready branch:
`pr/req-waiting-timeout` @ `6baf9e5d7e` on `upstream/main` @ `b524de2de6`.

## 2. Does it do what it says

**Unit tests.** The four touched unit files pass in a real environment on the pin (both versions) and
on the PR-ready head on current `upstream/main`, where the full pre-commit suite also passes on the 13
changed files. A sweep of the 94 unit files of `managers/` and `entrypoints/`: 93 pass; the one that
fails (`test_hisparse_unit.py`) fails without the patch too.

**Debug ladder** (`scripts/prb_ladder.py`): a server with one slot, a long greedy request holding it,
bounded requests queued behind it.

| Build | GPUs | Runs | Checks passed |
|---|---|---|---|
| first version | 1 | dummy weights, real model, real model with a 2 s global bound, unpatched control | 17, 17, 5, 2 of 17, 17, 5, 2 |
| final version, from a second source tree | 1 | real model, global bound | 17, 5 |
| final version, installed | 1 | all four | 17, 17, 5, 2 |
| final version, installed | 2, `--tp-size 2` | real model, global bound | 17, 5 |

What the 17 checks of the main run establish, on the real model:

- a request with `waiting_timeout: 1` is refused after 1.00–1.02 s on `/generate`, `/v1/completions` and
  `/v1/chat/completions`: HTTP 503 `Request waiting timeout reached.` when not streaming, HTTP 200 with
  the same error inside the stream when streaming; no token is produced;
- the request holding the slot finishes untouched; a request with a loose bound (3600 s) and one with
  none wait for the slot and are served;
- `0`, `-1`, `"abc"` and a 400-digit integer are answered with 400 and the server stays healthy.

With `SGLANG_REQ_WAITING_TIMEOUT=2`: a request asking for 30 s is refused at 2.0 s, one asking for 0.5 s
at 0.5 s, one without the field at 2.0 s. On a server without the patch the field is ignored: the
request waits and is served.

## 3. What it costs when it is not used

microseconds per call, best of 9, one CPU core of the node):

| Build, state | empty queue | 1000 queued | 10 000 queued |
|---|---|---|---|
| unpatched, no global bound | 1.20 | 1.19 | 1.18 |
| unpatched, global bound set | 1.29 | 58.4 | 1055 |
| **final, no bound of either kind ever seen** | 1.19 | 1.18 | 1.18 |
| **final, global bound set, no request bound** | 1.33 | 60.2 | 1003 |
| final, field seen once, no queued request carries one | 1.31 | 77.3 | 1378 |
| final, every queued request carries a bound | 1.32 | 98.5 | 1620 |
| first version, global bound set, no request bound | 1.29 | 90.8 | 1527 |

A server that never sees the field does what it did (a sticky flag keeps the queue from being walked).
A server that uses only the global bound pays 3 % more per scan; the first version of the patch cost it
56 %, which is why the scan was rewritten. With the field in use a scan costs about 0.1 µs per queued
request.

## 5. What it is for (U1)

One server with `--max-running-requests 128 --enable-priority-scheduling --disable-priority-preemption`.
Chat requests (256-token prompt, 128 output tokens, `priority` 1; objective: first token within 2 s
and 100 ms per token) arrive at 0.3 of the chat capacity and at 1.5 of it for the last 20 s of every
minute. Batch requests (1024-token prompt, 256 output tokens, `priority` 0; objective: done within
40 s) arrive at 0.5 of the batch capacity throughout. 180 s, about 10 000 requests per run, the same
seeded request list on every arm. Capacities are closed-loop measurements of each class alone:
65.7 and 19.1 req/s (66.6 and 19.5 when re-measured in P3).

| arm | runs | chat | batch | all | refused | wasted output tokens |
|---|---|---|---|---|---|---|
| no bound | 2 | 31.5 % | 50.3 % | 34.7 % | 0 % | 63 % |
| global 1.5 s | 3 | 78.9 % | 67.5 % | 77.0 % | 23.0 % | 0 % |
| global 5 s | 2 | 37.4 % | 66.2 % | 42.3 % | 16.5 % | 44 % |
| global 20 s | 2 | 31.7 % | 75.3 % | 39.1 % | 4.2 % | 52 % |
| global 30 s | 2 | 32.3 % | 81.0 % | 40.6 % | 3.2 % | 51 % |
| **per request: chat 1.5 s, batch 30 s** | 3 | **79.0 %** | **100.0 %** | **82.6 %** | 17.4 % | 0 % |
| per request: chat 1.5 s, batch none | 2 | 78.9 % | 100.0 % | 82.5 % | 17.5 % | 0 % |
| no bound; the chat client hangs up after 1.5 s without a token | 2 | 69.9 % | 100.0 % | 75.0 % | — | — |

Percentages are SLO attainment (requests that met their objective / requests sent), means over the
runs; the standard deviations are at most 1.5 pp except for batch under "no bound" (5.3). "Wasted" is
the share of generated output tokens that went to requests which then missed their objective.

Reading:

- No single global value serves both classes. A bound short enough for chat (1.5 s) drops a third of
  the batch requests, which are waiting on purpose behind the chat bursts. Every longer bound lets
  chat requests be served long after they stopped being useful, and attainment falls to about 40 %.
- With per-request bounds chat is where the 1.5 s global bound puts it (79.0 against 78.9 %) and every
  batch request finishes in time (100.0 against 67.5 %).
- The batch class does not need a bound at all: bounding only the chat requests gives the same result.
  Nothing has to be configured on the server.
- A client that hangs up instead does worse on chat by 9 pp (the server finds a disconnected queued
  request on a 4 s poll, and a client cannot tell queued from running).

**A3.1′ passes**: batch +32.5 pp against the 1.5 s global bound (required ≥ 10 pp and 3 σ = 2.1), chat
+0.1 pp (required ≥ −3 pp), total +5.6 pp against the best global arm (required ≥ 3 pp and 3 σ = 1.0).

The queue model used to choose this use case (`scripts/prb_sim.py`, [`prb/sim.md`](prb/sim.md)) had
predicted 34.9, 75.1, 44.2, 41.5, 43.0 and 83.3 % for the first six rows.

**Heavier bursts (U1b).** The same use case with chat bursts at 2.0 instead of 1.5 of the chat
capacity:

| arm | runs | chat | batch | all |
|---|---|---|---|---|
| no bound | 1 | 19.3 % | 23.8 % | 19.9 % |
| global 1.5 s | 2 | 64.7 % | 67.3 % | 65.1 % |
| per request: chat 1.5 s, batch 30 s | 2 | 64.6 % | 100.0 % | 69.6 % |

The same picture: chat equal, batch +32.7 pp, total +4.5 pp (the model had said 19, 64 and 71 %).

## 6. What it does not do (U2)

The same two classes on a server with the default first-come-first-served order: chat at 0.4 of its
capacity throughout, batch at 2.0 of its capacity for 15 s of every minute.

| arm | runs | chat | batch | all | refused |
|---|---|---|---|---|---|
| no bound | 1 | 38.2 % | 100.0 % | 54.3 % | 0 % |
| global 1.5 s | 2 | 87.7 % | 52.7 % | 78.5 % | 21.5 % |
| global 30 s | 1 | 38.3 % | 100.0 % | 54.3 % | 0 % |
| per request: chat 1.5 s, batch 30 s | 2 | 60.8 % | 100.0 % | 71.1 % | 28.9 % |

Under FCFS the requests that are allowed to wait stay in the queue, reach its head and take the slots,
so the per-request bound moves all the shedding onto the chat class: batch goes from 53 to 100 % and
chat from 88 to 61 %. In total it is 7.4 pp **below** a global bound tuned to the chat objective. The
model had predicted the per-class figures (chat 87 → 56, batch 49 → 100) and a tie in total for a
batch class twice as expensive as chat; here it is 3.4 times as expensive, so serving every batch
request costs more chat requests than it saves. This is reported, not gated (A3.2′): the field is for
deployments that order their queue, or for callers that need an explicit refusal — not a way to raise
attainment under FCFS.

## 8. Limits

- One model, one node type, one workload shape per use case (plus the heavier-burst variant); two or
  three seeds per arm.
- The chat and batch objectives and the two bounds (1.5 s, 30 s) were fixed before the runs, but they
  are choices; a different objective moves every number.
- U4 ran on the first version of the patch only; on the final build the field and the global knob were
  compared in the two-GPU runs (§4). U3 ran on both.
- Not exercised: PD disaggregation, the msgpack IPC path (`SGLANG_USE_PICKLE_IPC=0`), the embedded Rust
  server and `sgl-model-gateway`, sessions (`session_params` requests do not carry the field), more
  than two GPUs.
- Requests are synthetic (random token ids, fixed output length, greedy), so that every arm does the
  same work.
