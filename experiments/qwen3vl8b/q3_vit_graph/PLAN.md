## Amendment log — 2026-09-29, pre-data

A five-reviewer, five-verifier audit of the first version (`ab78ce0`) found blocking defects in the
runner and design errors in the pre-registration. Data had not been collected, so the
pre-registration is corrected here rather than in an outcome section. What changed and why:

| id | change | reason |
|---|---|---|
| D1 | The predictor's `U` is built from the **unprofiled** `VIT_TIMING` CPU wall (W_v) minus the trace's GPU busy time (G_v); the trace's own CPU wall is kept only as a secondary column, with `profiler_inflation = W_prof − W_v` recorded | the profiler adds host overhead to every op and launch; its CPU wall overstates U by an amount comparable to the tolerance |
| D2 | H1 gains an **overlap** term: after the encoder there is no host sync, so the graph arm's CPU starts launching the LM earlier; `Δ̂ = U* − r − ΔG_rot + min(G_v, max(0, W_l − G_l))`, with the interval `[U* − r − ΔG_rot, W_v − r − ΔG_rot]`; W_l, G_l come from a sync-free eager profile (pilot server `off_notiming`) | the pilot's `Q3_VIT_TIMING` sync had removed exactly this overlap, so the sweep would not reproduce the pilot |
| D3 | The rotary implementation is a confound: with the graph on, `VisionAttention` uses the unfused `apply_rotary_pos_emb_native_eager` (≈ 14 extra kernels per layer). A measurement-only switch `Q3_VIT_EAGER_ROTARY=1` forces it on an eager server (`off_rot`); `ΔG_rot = G_busy(off_rot) − G_busy(off)` enters the prediction | otherwise the graph arm carries extra GPU work that grows with S and the large sizes fail the tolerance for the wrong reason |
| D4 | Tolerance per size `tol_S = max(1 ms, 0.25·\|pred\|, 2·SE_S)`, SE from the per-block savings; a size is **non-informative** if `2·SE > \|pred\| + 1 ms`; pass rule: ≥ 4 informative sizes, at most 1 miss; blocks: 3 per size, 4 for 720p and 1080p | v3's cell-to-cell CV (≈ 1.6 %) is above 1 ms at 720p/1080p, so a correct model would fail "≥ 5/6" by noise |
| D5 | H3 corrected: the graph key is the **patch count**, not the 32-px grid, and `random:256x256-720x1280` draws heights 256–720 and widths 256–1280. 267 keys are possible; 300 draws give ≈ 165 ± 6 captures, a hit rate ≈ 45 % (by grid: ≈ 26 %). Mean TTFT is the H3 metric | the first version counted grids and assumed portrait bounds |
| D6 | Output length 16 tokens instead of 128 (TTFT at c=1 is unaffected; the pilot checks this on 256² against 128) | halves the sweep's wall time, which pays for D4's extra blocks |
| D7 | H2 uses the **critical path**: `crit = max(CPU end, last GPU end) − CPU start` per window; the ViT term is `VIT_TIMING`'s GPU span; the remainder is named "outside forward" | the CPU wall of the prefill step excludes the LM's asynchronous GPU tail, which was being charged to "client-side" |
| D8 | G1 additionally requires `cudaGraphLaunch` inside `Q3_VIT_FORWARD` on the graph arm and far fewer kernel launches than eager; the runner logs one `VIT_CG_CALL` line per replay so engagement is counted per window, not from a lifetime counter | the first replay check could not fail |
| B1 | `--skip-server-warmup` on both arms; the text control on the graph arm must show **no** graph lines | the server's 32×32 warmup image pre-captured the 256-patch key, which made the first cell's expected capture count wrong |
| B2 | Every log scan starts at the post-launch offset and strips the `[start/end of libtorchcodec loading traceback]` blocks | ≈ 60 harmless import tracebacks at startup were counted as degradation |
| B3 | The text control samples from a downloaded ShareGPT file passed explicitly (`--dataset-path`); `check` requires it | `--dataset-name random` fetches ShareGPT on demand, which `HF_HUB_OFFLINE=1` forbids |
| B4 | `--enable-precise-embedding-interpolation` on both arms | graph mode uses the legacy position-embedding interpolation, which honours this flag (default False = half-pixel), while eager uses `linspace`; the arms differed in more than one variable, and §1's "bit-exact" was wrong |
| B5 | Parity compares the **encoder outputs** (`Q3_VIT_DUMP`, relative Frobenius error ≤ 2e-2) and reports text divergences with their top-1/top-2 margin instead of failing on them | bf16 rotary tables and the unfused rotary make byte-identical greedy text an unreasonable criterion |
| O1 | `--mem-fraction-static 0.75` on every server; capture lines carry `memory_reserved`; the mixed stage has a memory guard | each captured graph keeps a private memory pool that is never freed; ≈ 165 of them need 11–17 GB |
| O2 | Per-cell summaries are git-tracked (`results/cells/`), resume is block-granular, traces and the manifest are synced | "expiry costs one cell" was false: the resume state was in an ignored directory |

## 0. The question, in one paragraph

Issue #4 v3 established two things about the **LM** prefill CUDA graph on Qwen3-VL-8B: it pays only
while the prefill is short (material win up to N≈364 tokens, nothing resolvable from N≈720), and
images dilute its percentage effect through a **fixed cost** — 23.6 ms at N=208 — that
[`q1_report.md`](../v3_issue4/q1_report.md) calls "preprocessing and vision-encoder time that no
CUDA graph can touch". That sentence is true of the LM graph and was never tested for the encoder.
SGLang has shipped a **ViT CUDA graph** for Qwen3-VL since 2025-12 (`SGLANG_VIT_ENABLE_CUDA_GRAPH=1`,
PR #15320) that this lab has never measured. Q3 asks how the image's added time splits into
(a) launch overhead inside the vision encoder, which a graph recovers, (b) the encoder's actual GPU
work, which nothing recovers, and (c) preprocessing and transport outside the model — and whether
(a) can be **predicted from an eager-mode profile alone**, without ever turning the graph on.

Consequences for the design: same **resolution** ⇒ 100 % hits after the first request (content is
irrelevant, so v3's random-content PNGs are the right input and the caches must stay off); every new
patch count ⇒ one capture plus permanent memory; cross-request ViT batching at c>1 puts the batch
layout into the key. c=1 and a fixed resolution is therefore the **upper bound** of what the feature
can do, and §2 H3 measures what happens when the shapes vary.

Model facts (HF configs): 8B encoder depth 27, hidden 1152, 16 heads, MLP 4304, patch 16, merge 2 ⇒
4 patches per visual token; DeepStack layers [8, 16, 24]. The 4B encoder is 24 × 1024, so 4B numbers
would not be comparable with v3; the 8B pin `0c351dd` is kept.

## 2. Hypotheses, pre-registered

### H1 — the graph's gain is predictable from an eager profile (primary) *(amended)*

For every image size S, the TTFT reduction from the ViT graph is bounded by the eager encoder's
un-overlapped CPU time and predicted by it plus the overlap the graph arm gains with the LM:

    U*(S)  = W_v(S) − G_v(S)          W_v: encoder CPU wall from VIT_TIMING (no profiler attached)
                                       G_v: GPU busy time inside Q3_VIT_FORWARD (eager trace)
    ΔG_rot = G_busy(off_rot) − G_v     extra GPU work of the unfused rotary the graph arm runs
    ovl    = min(G_v, max(0, W_l − G_l))   LM launch time the graph arm can now hide behind the
                                           encoder's GPU work (W_l, G_l from the sync-free profile)
    Δ̂_lo   = U* − r − ΔG_rot,   Δ̂ = Δ̂_lo + ovl,   Δ̂_hi = W_v − r − ΔG_rot,   r = 1.0 ms

`r` is the graph arm's residual — one graph launch, three buffer copies and the un-graphed eager
prologue — fixed at 1.0 ms before seeing data.

*Pass per size:* |Δ_measured − Δ̂| ≤ tol_S, tol_S = max(1.0 ms, 0.25·|Δ̂|, 2·SE_S), SE_S from the
per-block savings. A size is *non-informative* if 2·SE_S > |Δ̂| + 1 ms and is reported but not
judged. *H1 supported* if ≥ 4 image sizes are informative with at most 1 miss, the text-only
control moves less than the 3.6 % resolution floor, the saving is non-increasing in S (1 ms slack)
and 1080p is inside the floor. Only sizes whose cells are all VERIFIED count.

Why it would matter: the same accounting was the *surviving hypothesis* of IMG-R for the LM stage
("the graph recovers only the launch overhead not already hidden behind GPU execution"), but it was
never tested with a trace-derived prediction. If it holds on a second, structurally different stage,
it is a stage-agnostic rule an operator can apply from one eager profile — no A/B run needed to decide
where graphs pay. Orders of magnitude expected (priors, **not** the test): 600–800 launches per
encoder call; U* ≈ 5–15 ms at 256², decaying towards 0 at 1080p.

| workload | image | visual tokens | ViT patches | prior Δ (ms) | prior effect on TTFT |
|---|---|---|---|---|---|
| `R0_text` | none | 0 | 0 | 0 | 0 (control) |
| `R1_256` | 256×256 | 64 | 256 | 5–15 | −9 % … −27 % |
| `R2_360p` | 640×360 | 220 | 880 | 5–12 | −8 % … −19 % |
| `R3_512` | 512×512 | 256 | 1024 | 4–10 | |
| `R4_640` | 640×640 | 400 | 1600 | 3–8 | |
| `R5_720p` | 1280×720 | 880 | 3520 | 1–4 | 0 … −4 % (at the floor) |
| `R6_1080p` | 1920×1080 | 2040 | 8160 | ≈ 0 | inside the floor |

### H2 — what the "fixed cost" is made of *(amended: critical path)*

At 256² the encoder call (its critical path, `VIT_TIMING`'s GPU span) is ≥ 40 % of the image's
TTFT, and ≥ 60 % of the encoder call is un-overlapped launch time (U*/W_v). From 720p upward the
encoder's GPU busy time exceeds its un-overlapped time (G_v > U*: compute-dominated, not
recoverable). The remainder, "outside forward" = TTFT − queue − prefill-step critical path (HTTP,
base64 and PNG decode, image processor, tokenisation, transport, first-token streaming), is reported
separately with the request's PNG size, because random-content PNGs do not compress (720p ≈ 2.7 MB,
3.7 MB as base64) and that part is a benchmark artifact, not a model cost.

*Falsified if* U* at 256² is below 3 ms — then the fixed cost really is preprocessing plus compute
and the ViT graph is a non-lever.

### H3 — exact-shape keys under varied resolutions *(amended)*

With 300 requests whose heights are drawn uniformly from 256–720 px and widths from 256–1280 px
(fixed seed, same sequence on both arms), the exact-shape design captures once per distinct patch
count. 267 counts are possible; 300 draws should hit ≈ 165 ± 6 distinct ones, i.e. a **hit rate
≈ 45 %** by key (≈ 26 % by 32-px grid). Prediction: the graph arm's **mean** TTFT is worse than
eager (each capture costs ≥ 100 ms), while repeated shapes still gain what H1 predicts for their
size. This turns the "real traffic is different" caveat into a measured number and motivates padding
to buckets, which is how the LM prefill graph already works.

### What this is and is not

It is one model on one GPU class, driven at c=1: a **mechanism study with an upper bound**, not a
deployment recommendation. A publishable finding would additionally need (i) the same predictor
checked on the LM stage with the LM graph (PR #33726's branch), (ii) a second model with the same
graph runner (Qwen2.5-VL-7B), (iii) a second GPU class (RADIX has H100s), (iv) hit-rate analysis on a
real resolution distribution, and (v) ideally a bucketed-ViT-graph prototype that converts the upper
bound into a deployable gain. Q3 is the first of these steps and is designed so its data feed the
others unchanged. A by-product for upstream: under default flags the graph and eager paths compute
different position embeddings (B4); `parity --with-default-interp` records the size of that
difference as evidence for an issue.

## 3. Design

**Stack.** RADIX node, `tools/radix/setup_node.sh` with `SGLANG_REF=89e1316eae` (the SHA the patch
was written against; `check` enforces it), conda env `sgl-profiler`, CUDA 13.0 toolkit, torch 2.13
cu130 — the production-representative stack verified on 09-29. Model `Qwen/Qwen3-VL-8B-Instruct` @
`0c351dd` (17 GB), served from the snapshot path so `HF_HUB_OFFLINE=1` holds; `check` requires every
safetensors shard and the ShareGPT file.

**Arms.** `off` / `on` = `SGLANG_VIT_ENABLE_CUDA_GRAPH` 0 / 1. Nothing else differs; the env var is
read at server start, so every cell is its own server. The pilot adds two eager helpers: `off_rot`
(unfused rotary forced, for ΔG_rot) and `off_notiming` (no timing syncs, for W_l/G_l).

**Invariants, all explicit (in `scripts/q3_common.py`):**

| flag | why |
|---|---|
| `--cuda-graph-backend-prefill disabled` | LM graph off on both arms; main auto-disables it for multimodal, saying so keeps the arm honest |
| `--mm-attention-backend fa3` | required by the ViT graph; pinned rather than resolved |
| `--mm-feature-transport cuda_ipc` | #4's standard condition; also the Hopper default now |
| `--attention-backend flashinfer` | LM stage exactly as v3 pinned it; not under test |
| `--disable-radix-cache`, `--chunked-prefill-size 8192` | as v3 |
| `--mm-preprocess-cache-size-mb 0`, `SGLANG_VLM_CACHE_SIZE_MB=0` | no retention anywhere: every request runs the full path |
| `--enable-request-time-stats-logging` | per-request queue duration for the decomposition |
| `--skip-server-warmup` *(amended)* | the warmup image would pre-capture the 256² key |
| `--enable-precise-embedding-interpolation` *(amended)* | both arms interpolate position embeddings with linspace |
| `--mem-fraction-static 0.75` *(amended)* | room for the mixed stage's graph pools; c=1 never uses the KV pool |
| `--host 127.0.0.1` | node rule |

**Client.** `python -m sglang.benchmark.serving --backend sglang-oai-chat`, random-content PNG, one
image per request, 128 text tokens, **16 output tokens** *(amended)*, c=1, seed 1 — v3's IMG-R
generator for the flags and the pixels, so `R1_256`/`R2_360p`/`R4_640`/`R5_720p`/`R6_1080p` are
v3's `R1_tiny`/`R2_360p`/`R6_640`/`R3_720p`/`R5_1080p` on the new stack; `R3_512` is new. The text
control samples ShareGPT text like v3's `R0_text`, from a file passed explicitly.

**Blocking and gates.** Sweep: per workload, blocks in A/B then B/A order (`off,on,on,off`), one
rep of 200 prompts after 20 warmup prompts per cell, one server per cell; **3 blocks per size, 4 for
720p and 1080p** *(amended)*. Paired effect per block; gate G2 (Q1's rule): spread of paired
effects ≤ 3 pp or ≤ half the effect, else the workload is flagged WEAK. A block counts only when
both of its cells are OK; a half block is re-run in full.

**Engagement verification (no number is quotable without it).** The measurement patch adds
`VIT_CG capture key=… capture_ms=… reserved_mib=…`, one `VIT_CG_CALL` line per replay and a
`VIT_CG_STATS` line every 50 replays to the runner, and `VIT_TIMING patches= graph= cpu_wall_ms=
gpu_span_ms=` around the encoder call when `Q3_VIT_TIMING=1`. Scans start at the post-launch log
offset and drop the torchcodec import blocks. A cell is VERIFIED only if: the `on` arm's captures
plus replays cover its requests and it captured at most one shape; eager arms and the text control
show **no** graph lines; `/server_info` resolves to `cuda_ipc` / `fa3` / prefill `disabled`; every
prefill batch logs `cuda graph: False`; at least one prefill batch reached the server; no degradation
signal (`falling back to non-IPC transport`, `MmItemMemoryPool`, `PCG capture stream`, OOM,
tracebacks). G1 additionally requires `cudaGraphLaunch` inside `Q3_VIT_FORWARD` and far fewer kernel
launches on the `on` arm's trace.

**Decomposition method.** Pilot only. Four servers: `off` and `on` with `Q3_VIT_TIMING=1` (one
stream sync before and one after the encoder, identical on both arms), `off_rot`, and `off_notiming`
(no syncs). Per workload and server: 5 warmup requests, one torch-profiler capture of 5 requests
(`/start_profile` … `/stop_profile`, CPU+GPU, no stacks), and 30 measured requests where timing is
on. `scripts/parse_trace.py` splits the trace by the `Q3_STEP_EXTEND` / `Q3_VIT_FORWARD`
annotations and reports CPU wall, GPU busy (union of kernel intervals matched by correlation id,
time-window fallback), critical path, launch and graph-launch counts, and GPU time by kernel name.
The sweep runs with timing **off**, so its TTFTs carry no sync.

**Parity first** *(amended)*. Both arms encode five greedy fixtures (two text, two 336² stripe
images, one 512² stripe image) with `Q3_VIT_DUMP` on; the encoder outputs must agree to a relative
Frobenius error ≤ 2e-2 per image, and the `on` arm must show exactly two captures. Text divergences
are reported with the eager arm's top-1/top-2 margin at the first differing token (< 0.5 nat is
benign) and do not fail parity by themselves. A failure stops the experiment and becomes the finding.

**Instrumentation patch.** `patches/q3_vit_instrumentation.patch`, 197 lines over three files,
measurement-only, applied on the node's checkout after the build, never pushed anywhere (the same
rule as v3's `PCG_STATS`, manifest §7). It adds counters, the timing line, the output dump, the
eager-rotary switch and `record_function` names; it does not alter any computation on either arm.

## 5. Operations (details in RUNBOOK.md)

- Everything runs in tmux session `sgl-graph` on the node (windows `setup`, `models`, `run`); the Mac
  drives it over ssh and never leaves credentials or agents on the node. The `run` window activates
  the conda env explicitly and uses `set -o pipefail`, so a failed stage stops the chain.
- **Backups** *(amended)*. `scripts/sync_from_node.sh` on the Mac rsyncs `results/` (tracked
  `cells/` and summaries plus raw jsonl), the setup and server logs, the manifest and the profiler
  traces every 2 minutes, and commits only the tracked part to `exp/q3-vit-graph` with a path-scoped
  commit pushed to that branch explicitly. An assignment expiry (home wiped) costs at most one block.
- **Stop.** `touch ~/sgl/q3/STOP` on the node: the runner finishes the current block, writes
  `sweep.json`, exits 3; a stale STOP file is cleared when a stage starts. The monitor stops the run
  if a stage exceeds twice its budget, two cells fail in a row, G1 says STOP, or fewer than 30 min
  remain without an extension.
- **End of run (complete or stopped)** *(amended)*: stop the sync loop → `report_q3.py` and the
  manifest on the node → final sync with traces → rsync dry-runs list nothing pending →
  `origin/exp/q3-vit-graph == HEAD` → only then `radix release` → Outcome section here, `plan.md`
  §12.6, `context/` handoff.

## 6. Risks

| risk | mitigation |
|---|---|
| The ViT graph path breaks on this stack (fa3 + CUDA 13) | parity runs first; a crash or divergence is itself the result |
| Correlation-id matching misses graph-launched kernels | time-window fallback is used automatically and recorded per window; launch counts come from the runtime events, which always correlate |
| `Q3_VIT_TIMING` syncs perturb the pilot | pilot numbers feed prediction and decomposition only; the overlap term is taken from the sync-free server; the sweep runs without timing |
| Random-PNG decode dominates large images | reported as the "outside forward" term with PNG bytes; flagged as artifact, never folded into the encoder |
| Sweep overruns | STOP file at any block boundary; `--prompts 150` fallback; the design resumes at block granularity |
| Mixed stage exhausts GPU memory | `--mem-fraction-static 0.75` leaves ≈ 35 GB; the guard kills the client above 95 % and the partial run is reported |
| Cross-stack comparison with v3's LM numbers | qualitative only; the same-stack LM check is future work on the PR branch |
