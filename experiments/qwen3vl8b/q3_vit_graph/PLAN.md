# Q3 — Is the image's "fixed cost" untouchable? ViT CUDA graphs on Qwen3-VL-8B

> **Status: pre-registered 2026-09-29, not run.** Branch `exp/q3-vit-graph`. Everything below was
> written before any measurement; the Results section of `results/q3_report.md` is generated by
> `scripts/report_q3.py` and this file is only amended afterwards with a dated "Outcome" section.
> Commands: [`RUNBOOK.md`](RUNBOOK.md). Code: [`scripts/`](scripts/). Measurement patch:
> [`patches/q3_vit_instrumentation.patch`](patches/q3_vit_instrumentation.patch).

## 0. The question, in one paragraph

Issue #4 v3 established two things about the **LM** prefill CUDA graph on Qwen3-VL-8B: it pays only
while the prefill is short (material win up to N≈364 tokens, nothing resolvable from N≈720), and
images dilute its percentage effect through a **fixed cost** — 23.6 ms at N=208 — that
[`q1_report.md`](../v3_issue4/q1_report.md) calls "preprocessing and vision-encoder time that no
CUDA graph can touch". That sentence is true of the LM graph and was never tested for the encoder.
SGLang has shipped a **ViT CUDA graph** for Qwen3-VL since 2025-12 (`SGLANG_VIT_ENABLE_CUDA_GRAPH=1`,
PR #15320) that this lab has never measured. Q3 asks how the image's added time splits into
(a) launch overhead inside the vision encoder, which a graph recovers, (b) the encoder's actual GPU
work, which nothing recovers, and (c) preprocessing and transport outside the model — and whether
(a) can be **predicted from an eager-mode trace alone**, without ever turning the graph on.

## 1. Mechanism facts (read from source, `sgl-project/sglang` `upstream/main` @ `89e1316eae`, 2026-09-28)

| Nightly correctness coverage exists: Qwen3-VL-8B with the graph on, MMMU ≥ 0.60 | `test/manual/nightly/test_vlms_vit_cuda_graph.py` |

Consequences for the design: same **resolution** ⇒ 100 % hits after the first request (content is
irrelevant, so v3's random-content PNGs are the right input and the caches must stay off); every new
resolution ⇒ one capture plus permanent memory; cross-request ViT batching at c>1 puts the batch
layout into the key. c=1 and a fixed resolution is therefore the **upper bound** of what the feature
can do, and §2 H3 measures what happens when the shapes vary.

Model facts (HF configs): 8B encoder depth 27, hidden 1152, 16 heads, MLP 4304, patch 16, merge 2 ⇒
4 patches per visual token; DeepStack layers [8, 16, 24]. The 4B encoder is 24 × 1024, so 4B numbers
would not be comparable with v3; the 8B pin `0c351dd` is kept.

## 2. Hypotheses, pre-registered

### H1 — the graph's gain is predictable from the eager trace (primary)

For every image size S, the TTFT reduction from the ViT graph equals the eager encoder's
**un-overlapped CPU time** minus a fixed residual:

    Δ(S) = U(S) − r,   U(S) = CPU wall of the eager encoder call − GPU busy time inside it,   r = 1.0 ms

`U` is read from a torch-profiler trace of the **eager arm only** (`Q3_VIT_FORWARD` window,
kernels matched by CUPTI correlation id). `r` is the graph arm's residual — one graph launch, three
buffer copies and the un-graphed eager prologue — fixed at 1.0 ms before seeing data.

*Pass:* |Δ_measured − Δ_predicted| ≤ max(1.0 ms, 25 % of Δ_predicted) for ≥ 5 of 6 image sizes, and
the text-only control moves less than the 3.6 % resolution floor. *Qualitative shape:* U falls
monotonically with S; Δ is non-increasing in S; Δ at 1080p is inside the floor.

Why it would matter: the same accounting was the *surviving hypothesis* of IMG-R for the LM stage
("the graph recovers only the launch overhead not already hidden behind GPU execution"), but it was
never tested with a trace-derived prediction. If it holds on a second, structurally different stage,
it is a stage-agnostic rule an operator can apply from one eager profile — no A/B run needed to decide
where graphs pay. Orders of magnitude expected (priors, **not** the test): 600–800 launches per
encoder call; U ≈ 5–15 ms at 256², decaying to ≈ 0 at 1080p.

| workload | image | visual tokens | ViT patches | prior Δ (ms) | prior effect on TTFT |
|---|---|---|---|---|---|
| `R0_text` | none | 0 | 0 | 0 | 0 (control) |
| `R1_256` | 256×256 | 64 | 256 | 5–15 | −9 % … −27 % |
| `R2_360p` | 640×360 | 220 | 880 | 5–12 | −8 % … −19 % |
| `R3_512` | 512×512 | 256 | 1024 | 4–10 | |
| `R4_640` | 640×640 | 400 | 1600 | 3–8 | |
| `R5_720p` | 1280×720 | 880 | 3520 | 1–4 | 0 … −4 % (at the floor) |
| `R6_1080p` | 1920×1080 | 2040 | 8160 | ≈ 0 | inside the floor |

### H2 — what the "fixed cost" is made of

At 256² the encoder call is ≥ 40 % of the image's TTFT and ≥ 60 % of the encoder call is
un-overlapped launch time (recoverable). From 720p upward the encoder's GPU busy time exceeds its
un-overlapped time (compute-dominated, not recoverable). The client-side remainder
(TTFT − queue − prefill step: HTTP, base64 and PNG decode, image processor, transport, first-token
streaming) is reported separately with the request's PNG size, because random-content PNGs do not
compress (720p ≈ 2.7 MB, 3.7 MB as base64) and that part is a benchmark artifact, not a model cost.

*Falsified if* the encoder's un-overlapped time at 256² is below 3 ms — then the fixed cost really
is preprocessing plus compute and the ViT graph is a non-lever.

### H3 — exact-shape keys under varied resolutions

With 300 requests whose resolutions are drawn uniformly from 256×256 … 1280×720 (fixed seed, same
sequence on both arms), the exact-shape design captures once per distinct 32-px grid. 33 × 15 = 495
grids are possible; 300 uniform draws should hit ≈ 225 distinct ones, i.e. a hit rate ≈ 25 %.
Prediction: the graph arm's **mean** TTFT is worse than eager (each capture costs ≥ 100 ms), while
repeated shapes still gain what H1 predicts for their size. This turns the "real traffic is different"
caveat into a measured number and motivates padding to buckets, which is how the LM prefill graph
already works.

### What this is and is not

It is one model on one GPU class, driven at c=1: a **mechanism study with an upper bound**, not a
deployment recommendation. A publishable finding would additionally need (i) the same predictor
checked on the LM stage with the LM graph (PR #33726's branch), (ii) a second model with the same
graph runner (Qwen2.5-VL-7B), (iii) a second GPU class (RADIX has H100s), (iv) hit-rate analysis on a
real resolution distribution, and (v) ideally a bucketed-ViT-graph prototype that converts the upper
bound into a deployable gain. Q3 is the first of these steps and is designed so its data feed the
others unchanged.

## 3. Design

**Stack.** RADIX node, `tools/radix/setup_node.sh` with `SGLANG_REF=89e1316eae` (the SHA the patch
was written against), conda env `sgl-profiler`, CUDA 13.0 toolkit, torch 2.13 cu130 — the
production-representative stack verified on 09-29. Model `Qwen/Qwen3-VL-8B-Instruct` @ `0c351dd`
(17 GB), served from the snapshot path so `HF_HUB_OFFLINE=1` holds.

**Arms.** `off` / `on` = `SGLANG_VIT_ENABLE_CUDA_GRAPH` 0 / 1. Nothing else differs; the env var is
read at server start, so every cell is its own server.

**Invariants, all explicit (in `scripts/q3_common.py`):**

| flag | why |
|---|---|
| `--cuda-graph-backend-prefill disabled` | LM graph off on both arms; main auto-disables it for multimodal, saying so keeps the arm honest |
| `--mm-attention-backend fa3` | required by the ViT graph; pinned rather than resolved |
| `--mm-feature-transport cuda_ipc` | #4's standard condition; also the Hopper default now |
| `--attention-backend flashinfer` | LM stage exactly as v3 pinned it; not under test |
| `--disable-radix-cache`, `--chunked-prefill-size 8192` | as v3 |
| `--mm-preprocess-cache-size-mb 0`, `SGLANG_VLM_CACHE_SIZE_MB=0` | no retention anywhere: every request runs the full path |
| `--enable-request-time-stats-logging` | per-request queue duration for the decomposition |
| `--host 127.0.0.1` | node rule |

**Client.** `python -m sglang.benchmark.serving --backend sglang-oai-chat`, random-content PNG, one
image per request, 128 text tokens, 128 output tokens, c=1, seed 1 — byte-for-byte v3's IMG-R
generator, so `R1_256`/`R2_360p`/`R4_640`/`R5_720p`/`R6_1080p` are v3's `R1_tiny`/`R2_360p`/
`R6_640`/`R3_720p`/`R5_1080p` on the new stack; `R3_512` is new.

**Blocking and gates.** Sweep: per workload, blocks in A/B then B/A order (`off,on,on,off`), one
rep of 200 prompts after 20 warmup prompts per cell, one server per cell. Paired effect per block;
gate G2 (Q1's rule): spread of paired effects ≤ 3 pp or ≤ half the effect, else the workload is
flagged WEAK and gets a third block if time remains.

**Engagement verification (no number is quotable without it).** The measurement patch adds
`VIT_CG capture key=… capture_ms=…` and `VIT_CG_STATS captures= replays= keys=` lines to the
runner, and `VIT_TIMING patches= graph= cpu_wall_ms= gpu_span_ms=` around the encoder call when
`Q3_VIT_TIMING=1`. A cell is VERIFIED only if: the `on` arm shows exactly one capture per fixed
shape and replays ≈ requests − 1; the `off` arm shows **no** graph lines; `/server_info` resolves to
`cuda_ipc` / `fa3` / prefill `disabled`; every prefill batch logs `cuda graph: False`; no degradation
signal (`falling back to non-IPC transport`, `MmItemMemoryPool`, `PCG capture stream`, tracebacks).
The pilot additionally shows `cudaGraphLaunch` inside `Q3_VIT_FORWARD` on the `on` arm's trace.

**Decomposition method.** Pilot only: `Q3_VIT_TIMING=1` (one stream sync per request, identical on
both arms) plus one torch-profiler capture of 5 requests per workload and arm
(`/start_profile` … `/stop_profile`, CPU+GPU, no stacks). `scripts/parse_trace.py` splits the trace
by the `Q3_STEP_EXTEND` / `Q3_VIT_FORWARD` annotations and reports CPU wall, GPU busy (union of
kernel intervals matched by correlation id, with a time-window fallback), launch counts and
graph-launch counts. TTFT = client-side + queue + prefill step; prefill step = ViT + LM.
The sweep runs with timing **off**, so its TTFTs carry no sync.

**Parity first.** Both arms answer five greedy fixtures (two text, two 336² stripe images, one 512²
stripe image) and must agree byte-for-byte; a difference stops the experiment and becomes the finding.

**Instrumentation patch.** `patches/q3_vit_instrumentation.patch`, 156 lines, measurement-only,
applied on the node's checkout after the build, never pushed anywhere (the same rule as v3's
`PCG_STATS`, manifest §7). It adds counters, the timing line, and `record_function` names; it does
not alter any computation.

## 5. Operations (details in RUNBOOK.md)

- Everything runs in tmux session `sgl-graph` on the node (windows `setup`, `models`, `run`); the Mac
  drives it over ssh and never leaves credentials or agents on the node.
- **Backups.** `scripts/sync_from_node.sh` on the Mac rsyncs `results/` and the server logs every
  2 minutes and commits the summaries to `exp/q3-vit-graph`; an assignment expiry (home wiped) costs
  at most one cell. Raw jsonl, logs and traces stay under git-ignored `results/raw/`.
- **Stop.** `touch ~/sgl/q3/STOP` on the node: the runner finishes the current cell, writes
  `sweep.json`, exits 3. Rerunning the stage resumes. The monitor stops the run if a stage exceeds
  twice its budget, two cells fail in a row, G1 says STOP, or the 6 h cap is reached.
- **End of run (complete or stopped):** `report_q3.py` → final sync (`Q3_SYNC_TRACES=1` once) →
  commit/push → `radix release` → Outcome section here, `plan.md` §12.6, `context/` handoff.

## 6. Risks

| risk | mitigation |
|---|---|
| The ViT graph path breaks on this stack (fa3 + CUDA 13) | parity runs first; a crash or divergence is itself the result |
| Correlation-id matching misses graph-launched kernels | time-window fallback reported alongside; launch counts come from the runtime events, which always correlate |
| `Q3_VIT_TIMING` sync perturbs the pilot | pilot numbers are for prediction and decomposition only; the sweep runs without it |
| Random-PNG decode dominates large images | reported as the client-side term with PNG bytes; flagged as artifact, never folded into the encoder |
| Sweep overruns | STOP file at any cell boundary; `--prompts 150` fallback; the design is resumable |
| Cross-stack comparison with v3's LM numbers | qualitative only; the same-stack LM check is future work on the PR branch |
